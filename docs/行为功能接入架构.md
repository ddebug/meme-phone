# acsus 行为功能接入 meme-phone · 架构设计

> 版本：v1（2026-11-18）  
> 目标：把 acsus 已有的聊天行为能力接入 meme-phone，先定协议、状态与分层，再按批次实现。  
> 本文是架构与实施边界，不是一次性重写方案；未列出的现有聊天、API、预设、记忆逻辑保持原样。

---

## 1. 范围与现状

### 1.1 要接入的行为

按 `acsus-phone-standalone/toolkit/phone/messages/message-types/` 的现有类型，行为分为四组：

| 组 | acsus 类型 | meme 当前状态 |
| --- | --- | --- |
| 钱包类 | `transfer`、`redpacket`、`gift-membership`、`buy-membership` | 只有文字；没有钱包、会员、转账 |
| 计划类 | `plan`、`plan-story` | 只有角色日程 App；没有约定计划 |
| 联系人事件 | `friend-request`、`friend-added`、`friend-deleted`、`signature` | 通讯录可加角色；没有好友申请、个签历史 |
| 已有富消息 | `image`、`image-real`、`image-fake`、`emoji`、`poke`、`recalled`、`quote`、`forwarded`、`system` | 已有基础实现，但消息模型不统一 |

### 1.2 当前问题

1. `meme/data.js` 的 `pushMessage()` 只白名单保存 `text / image / emoji / forward / quote` 等字段，新行为字段会被丢掉。
2. `meme/apps/chat.js` 用三元表达式直接决定气泡，新增一种消息就要改一处渲染，容易变成第二个 acsus。
3. `meme/index.js` 的 `reply()` 把整段模型回复当成**一条**消息，没有 acsus 的多气泡、行为标签解析。
4. `meme/chat-transfer.js` 导入 acsus 时，把 `transfer / redpacket / plan / plan-story / 会员 / 好友事件` 降级成文字或系统消息，行为数据直接丢失。
5. acsus 的部分行为在**渲染时**产生副作用（例如收到转账就入账）。meme 不能沿用，否则刷新、重渲染、重复导入都会重复加钱。

### 1.3 非目标

- 不复制 acsus 的 jQuery / DOM 组件、`stateManager`、页面栈。
- 不实现真实支付；钱包与会员只做本地模拟数字和记录。
- 不改现有 API 请求、模型测试、模型拉取、LLM 方案、回复预设、记忆结构。
- 不重做整套手机主题；行为 UI 继续使用 frost 毛玻璃与现有三套主题。
- 不顺手重构群聊、朋友圈、日记、小剧场等其他 App。

## 2. 设计原则

1. **行为是数据，不是 DOM**：消息只保存 `kind + behavior`，渲染由注册表按类型分发。
2. **一个行为一个描述**：解析、渲染、上下文序列化、导入映射、菜单动作都挂在同一个行为定义上，避免五处各写一遍。
3. **领域服务持有状态**：钱包、会员、约定计划、好友申请各自有明确读写函数；UI 不直接改 `state`。
4. **副作用只发生一次**：创建消息、确认收到、接受计划等动作由命令层执行；渲染必须是纯函数。
5. **导入先还原历史，不重放交易**：ac sus 聊天记录导入默认只还原消息；不自动加钱、不自动开通会员、不自动改计划状态。
6. **可回退**：删除 / 重 roll / 撤回行为消息时，通过行为自己的 `rollback()` 处理关联状态，不能留孤儿数据。
7. **无弹窗**：新增交互使用页面内联展开或现有全屏子页；删除、拒绝等二次确认用内联确认态。
8. **单存档**：所有新状态仍写入 `meme-phone.json` 的同一个 `state`，通过 `normalize()` 补默认值。

## 4. 消息模型

### 4.1 基本结构

保留 meme 现有字段，新增一个可选的 `behavior` 对象。旧消息完全兼容。

```js
{
  id: 'm_x',
  from: 'me' | 'them' | 'system',
  at: 1760000000000,
  kind: 'text' | 'image' | 'emoji' | 'poke' | 'recalled' | 'forwarded'
       | 'transfer' | 'redpacket' | 'plan' | 'plan-story'
       | 'gift-membership' | 'buy-membership'
       | 'friend-request' | 'friend-added' | 'friend-deleted' | 'signature',
  text: '气泡上的一行摘要或正文',
  quote: null | { text, from },
  image: '', emoji: '', forward: null,
  behavior: null | {
    id: '行为关联的领域 ID',
    status: 'pending' | 'accepted' | 'rejected' | 'completed' | 'cancelled' | 'reversed',
    ...按类型附加字段
  }
}
```

### 4.2 各行为字段

| `kind` | `behavior` 必填字段 | 说明 |
| --- | --- | --- |
| `transfer` | `amount`、`note`、`txId`、`status` | 金额为正数；`txId` 对应钱包流水 |
| `redpacket` | `amount`、`note`、`txId`、`status` | 与转账共用钱包流水，类型不同 |
| `gift-membership` | `membershipType`、`months`、`duration`、`price`、`status` | 角色送用户 |
| `buy-membership` | `membershipType`、`months`、`duration`、`price`、`status` | 角色自己开通 |
| `plan` | `planId`、`title`、`status`、`initiator` | 计划发起 / 接受 / 拒绝 / 完成 |
| `plan-story` | `planId`、`storyId`、`status` | 计划执行后的故事 |
| `friend-request` | `requestId`、`text`、`status` | 好友申请 |
| `friend-added` | `requestId`、`contactId` | 已成为好友 |
| `friend-deleted` | `contactId` | 已被删除 |
| `signature` | `signature`、`actionType` | 修改 / 点赞 / 评论 |

约束：`behavior.id` 只作为关联键，不复制联系人、API、预设或记忆数据；不引入 `memoryId`。

### 4.3 `pushMessage()` 的改动

- 白名单增加 `behavior`，并对 `behavior` 做浅层 JSON 清洗。
- 新行为消息统一走 `pushMessage()`，保证 `at`、未读、`updatedAt` 一致。
- `messagePreview()` 增加行为摘要：`[转账] ¥88`、`[约定计划] 去看海`、`[会员] 送 1 个月 VIP` 等。

## 5. 行为注册表

### 5.1 定义接口

```js
registerBehavior({
  kind: 'transfer',
  label: '转账',
  icon: 'transfer',
  parse(text, ctx),          // AI 标签 -> null | Partial<BehaviorMessage>
  create(input, ctx),        // 用户操作 -> Partial<BehaviorMessage>
  render(message, ctx),      // 纯函数，返回 HTML 字符串
  preview(message),          // 会话列表 / 收藏页摘要
  context(message, ctx),     // 给模型的历史文本
  menu(message, ctx),        // 长按菜单项
  actions: { ... },          // 该类型允许的动作
  apply(message, ctx),       // 命令层调用，写领域状态
  rollback(message, ctx),    // 删除 / 重 roll 时撤销
  fromAcsus(raw, ctx),       // ac sus -> BehaviorMessage
  toAcsus(message, ctx),     // 可选，导出用
});
```

### 5.2 注册与兜底

- `behavior.js` 内维护 `Map<kind, definition>`。
- `parseReply(text, ctx)`：
  1. 如果文本包含 `[消息]`，只取消息区，按行拆成气泡，空行忽略；找不到 `[消息]` 时把整段当一条文字，保持现有兼容。
  2. 每个气泡按注册表顺序尝试 `parse()`；精确标签优先，未知标签降级为普通文字。
  3. 一条回复最多生成 30 个气泡；超出部分丢弃并返回提示，不无限解析。
- 渲染：`renderMessage(message, ctx)` 先按 `kind` 查注册表，查不到回退到 `text`，再查不到显示空字符串。
- 菜单：`messageMenu(message, ctx)` 汇总注册表条目和通用操作（复制、引用、转发、删除、收藏）。通用操作仍由 `chat.js` 处理，行为专属动作由注册表处理。

### 5.3 解析顺序

`friend-request`、`plan` 响应、`quote` 这类有重叠格式的标签必须先精确匹配，再走通用解析：

1. `[引用]#N[回复][约定计划]...` → `plan` 响应
2. `[引用]#N[回复]...` → `quote`
3. `[约定计划已完成]...` / `[约定计划]...` → `plan`
4. `[转账]...` / `[红包]...`
5. `[送会员]...` / `[开会员]...`
6. `[好友申请]...`
7. `[改个签]...`
8. `[戳一戳]` / `[表情]` / `[图片]` / `[转发]` / `[撤回]`
9. 普通文字

## 6. 领域层

### 6.1 状态切片

在 `emptyState()` / `normalize()` 增加以下字段，旧存档补默认值，不做迁移脚本：

```js
state.wallet = {
  balance: 0,
  transactions: [] // { id, contactId, type, direction, amount, note, messageId, status, at }
};

state.membership = {
  user: { type: 'none', expireAt: 0, queue: [], history: [] },
  byContact: {} // contactId -> { type, expireAt, queue, history }
};

state.appointments = {
  byContact: {} // contactId -> Plan[]；不要混用现有 state.plans（角色日程）
};

state.friendRequests = [] // { id, contactId, name, avatar, text, status, at }
state.signatures = {
  byContact: {} // contactId -> [{ id, text, actionType, at }]
};
```

明确的边界：

- `state.plans` 继续是「角色日程」；约定计划放 `state.appointments`，避免语义冲突。
- 会员不复制到 `contacts`，以 `state.membership.byContact` 为唯一源；联系人页只读取。
- 钱包流水保留 `messageId`，用于删除消息时回退。

### 6.2 钱包

```js
sendTransfer(state, { contactId, amount, note }) -> { tx, message }
receiveTransfer(state, { contactId, amount, note, messageId }) -> tx
refundTransfer(state, txId, reason) -> tx
deleteTransfer(state, txId) -> 是否删除
```

规则：

- 金额只接受 `0.01–10000`，最多两位小数。
- 用户转出先检查余额；余额不足返回 `insufficient`，不创建消息。
- 角色转来在消息创建成功后才入账；`(messageId, txId)` 双键去重。
- 红包与转账共用流水，`tx.type` 区分；不做随机金额分配。
- 删除 / 撤回已入账的转账消息：按方向回退；余额不足时不强制扣成负数，先把流水标 `reversed` 并返回需要用户处理的提示。

### 6.3 会员

```js
grantUserMembership(state, { type, months, price, from, messageId })
grantContactMembership(state, { contactId, type, months, price, messageId })
revokeMembership(state, target, messageId)
```

- 等级只保留 `none / vip / svip`；`annual-svip` 暂不在 meme 侧引入，12 个月只按 `svip` + 365 天处理，避免扩大规则。
- 同等级叠加；高等级插队、低等级排队沿用 acsus 的核心规则。
- 价格只做记录，不接真实支付。
- `messageId` 进入 `history`，重复导入 / 重渲染不重复开通。

### 6.4 约定计划

```js
createAppointment(state, { contactId, title, initiator, messageId })
respondAppointment(state, { contactId, planId, accept })
completeAppointment(state, { contactId, planId, story })
cancelAppointment(state, { contactId, planId })
```

计划字段：

```js
{
  id, contactId, messageId, title, initiator: 'me' | 'them',
  status: 'pending' | 'accepted' | 'rejected' | 'completed' | 'cancelled',
  createdAt, respondedAt, completedAt,
  story: null | { id, text, outcome, at }
}
```

规则：

- 创建计划前按 `messageId` 去重；同一消息只建一个计划。
- 只有 `pending` 能接受 / 拒绝；只有 `accepted` 能完成 / 取消。
- 计划故事先写 `story`，再写一条 `plan-story` 消息；不把故事正文塞进聊天普通气泡。
- 计划消息删除时，计划标 `cancelled` 并保留历史；不物理删除，避免已完成故事变孤儿。

### 6.5 好友与个签

```js
requestFriend(state, { contactId, text })
acceptFriend(state, requestId)
rejectFriend(state, requestId)
removeFriend(state, contactId)
updateSignature(state, { contactId, text, actionType })
```

- 好友申请只针对已存在但未加入通讯录的酒馆角色；通过后调用现有 `addContact()`。
- `friend-added / friend-deleted` 是事件消息，不重复改联系人；改联系人由命令层完成。
- 个签历史最多保留 50 条；`updateSignature` 同时更新 `contact.signature` 和 `state.signatures.byContact`。
- 个签长度沿用 acsus 的 80 字符上限。

## 7. AI 协议

### 7.1 注入位置

在 `meme/reply-context.js` 的回复上下文里增加一个可选的行为说明块，只有在对应行为开关开启时才注入：

```text
[可用行为]
[转账]金额|留言
[红包]金额
[约定计划]标题
[送会员]VIP/1个月
[开会员]VIP/1个月
[改个签]新签名
```

默认策略建议：

- 转账、红包、送会员、好友申请默认**关闭**，避免模型擅自产生金钱和联系人事件。
- 约定计划、戳一戳、表情、图片默认开启，沿用 acsus 的常用路径。
- 每个会话可覆盖全局开关，存 `chat.behavior`，不复制预设数据。

### 7.2 解析与执行

```text
模型返回
  -> parseReply()
  -> ParsedMessage[]
  -> 过滤 [不发]
  -> 逐条 pushMessage()
  -> 对每条调用 definition.apply()（只执行一次）
  -> 小剧场 sections 仍挂到最后一条可见消息
```

约束：

- `parseReply` 只解析文本协议，不直接写 state。
- `apply()` 必须支持 `dryRun`，导入预览和调试栏只预览不落账。
- 一次回复最多 1 条转账 / 红包、1 条计划、1 条会员、1 条好友申请；超出按普通文字降级。
- 所有行为标签必须可被 `context()` 原样还原成给模型看的文本，保证多轮一致。

### 7.3 请求上下文中的行为

`context()` 输出示例：

```text
[转账]88元 晚饭
[约定计划]周末去看海（待响应）
[约定计划已完成]周末去看海
[送会员]1个月VIP会员
[好友申请]我是上次那个…
```

不把钱包余额、会员到期时间等隐私状态塞进每轮上下文；需要时由系统块单独注入摘要。

所有气泡继续复用 `.mp-msg` / `.mp-bubble`；新样式只加在 `meme.css` 的 `.mp-bubble-transfer`、`.mp-bubble-plan` 等类上，不建立第二套气泡体系。

## 9. 导入 / 导出

### 9.1 acsus -> meme 映射

由行为定义提供 `fromAcsus()`，不再在 `chat-transfer.js` 里写 if/else 链：

| acsus `type` | meme `kind` | behavior |
| --- | --- | --- |
| `text` | `text` | — |
| `transfer` | `transfer` | `amount / message / status` |
| `redpacket` | `redpacket` | `amount / message` |
| `plan` | `plan` | `title / status` |
| `plan-story` | `plan-story` | `title / story` |
| `gift-membership` | `gift-membership` | `membershipType / months / duration / price` |
| `buy-membership` | `buy-membership` | 同上 |
| `friend-request` | `friend-request` | `text / status` |
| `friend-added` | `friend-added` | `contactId` |
| `friend-deleted` | `friend-deleted` | `contactId` |
| `signature` | `signature` | `signature / actionType` |
| `quote` | `text` + `quote` | 沿用现有引用结构 |
| `image` / `image-real` / `image-fake` | `image` | `image`；`image-fake` 加 `behavior.fake` |
| `emoji` / `poke` / `recalled` / `forwarded` | 对应已有 kind | 沿用现有字段 |

### 9.2 导入策略

- 默认 `mode: 'history'`：只还原消息与 `behavior` 元数据，不执行 `apply()`，不改钱包 / 会员 / 计划 / 好友状态。
- 导入后，行为气泡按历史记录展示；涉及余额的旧消息标「历史记录，未入账」，避免误导。
- 导入仍按消息 ID 去重、按时间排序、不覆盖现有聊天。
- `meme-phone-chat` 格式不升版本，`behavior` 作为可选字段；旧版本导入器忽略未知字段也不影响。
- 导出原样带 `behavior`；ac sus 导出目标格式不在本批强制实现，先保证 meme 自身往返。

### 9.3 删除 / 重 roll

- 删除普通消息：沿用现有逻辑。
- 删除行为消息：先调用 `rollback()`，再删消息；回退失败则保留消息并给出明确提示。
- 重 roll：新消息生成成功后再回退旧行为，不能先回退再等模型。

## 10. 状态与兼容

### 10.1 `normalize()` 的职责

- 新切片缺失时补默认值。
- 数组 / 对象字段做浅层类型检查，坏数据丢弃，不让页面崩。
- 保留旧 `state.plans`、`state.contacts`、`state.chats` 原样。
- `SCHEMA_VERSION` 从 1 升到 2；只做向后兼容读取，不做整包迁移。

### 10.2 不修改的结构

- API 预设：仍为 `{ id, name, engine, url, path, model, key, temp }`。
- LLM 方案：仍为 `{ id, name, apiId, replyId }`，不增加 `memoryId`。
- 回复预设：仍按现有条目结构。
- 记忆：仍按现有方案 / 角色开关。
- 角色卡：仍只读酒馆字段。

## 12. 验收与风险

### 12.1 必须通过

- 旧聊天记录、旧备份导入后页面不报错。
- 任何行为消息重复渲染不会重复加钱 / 开通会员 / 建计划。
- 删除行为消息能回退，且不会把余额扣成负数。
- 导入 acsus 记录时，六类行为消息至少能正确显示，不变成普通文字。
- 三套主题、日夜模式、手机宽度下无横向溢出；展开面板不顶乱聊天列表。
- 现有 API、LLM 方案、预设、记忆、酒馆 API 全部不回归。

### 12.2 主要风险

| 风险 | 处理 |
| --- | --- |
| acsus 字段命名不统一（`content` / `message` / `description`） | `fromAcsus()` 内部做字段归一，不让 UI 猜 |
| 用户已有 `state.plans` 角色日程 | 约定计划使用独立 `state.appointments` |
| 模型乱发 `[转账]` | 默认关闭，金额上限，单轮限一条 |
| 导入旧记录触发真实加钱 | 导入模式固定 `history`，不执行 `apply()` |
| 删除消息后状态残留 | 每个行为定义必须实现 `rollback()`；没有实现的不允许上线 |
| 气泡样式在像素主题下错位 | 新气泡只复用现有 `.mp-bubble` 基础，不引入独立尺寸 |
